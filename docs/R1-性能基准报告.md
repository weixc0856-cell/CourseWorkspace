# R1-2 性能基准报告

- **日期**：2026-11-07
- **范围**：Blender（Eevee / Cycles CPU / Cycles oneAPI GPU）、Manim（draft / final）、Remotion（并发 1 / 4）、FFmpeg（QSV / libx264 字幕烧录）
- **方法**：固定场景、单次冷/禁用缓存运行；脚本 `scripts/benchmark_render.py`；原始数据 `build/r1/benchmark/*.json` 与 `summary.json`

## 1. 环境

| 项 | 值 |
| --- | --- |
| CPU | 13th Gen Intel Core i7-13700K |
| GPU | Intel Arc A750（Blender Cycles 识别为 ONEAPI 设备） |
| Blender | 5.2.3 LTS |
| Manim | Community v0.22.0 |
| Remotion | 4.0.539 / Node v24.14.1 |
| FFmpeg | 8.1-full_build（h264_qsv、libx264、libass） |
| OS | Windows 11 Pro |

GPU 专用内存基线（桌面空闲）约 **5.1–5.2 GB**（Windows `GPU Adapter Memory` 计数器）。下表的 GPU 峰值包含该基线，不能全部归因于渲染。

## 2. Blender

固定程序化场景：立方体 + 地面 + 面积光 + 相机，1920×1080 / 30 fps / 60 帧（2.0 s），Cycles 8 samples。

| 引擎 | 耗时 | 每帧 | 进程峰值内存 | GPU 专用峰值 | 产物 |
| --- | --- | --- | --- | --- | --- |
| Eevee | **20.92 s** | 0.35 s | 1,324.8 MB | 6,418.6 MB | `build/r1-smoke/blender/bench-eevee.mp4` |
| Cycles CPU | **346.56 s** | 5.78 s | 2,953.6 MB | 5,230.2 MB（≈基线） | `build/r1-smoke/blender/bench-cycles-cpu.mp4` |
| Cycles oneAPI GPU | **291.78 s** | 4.86 s | 3,316.6 MB | 7,384.8 MB（≈基线 + 2.2 GB） | `build/r1-smoke/blender/bench-cycles-gpu.mp4` |

结论：

- 同一份小场景，**Eevee 比 Cycles 快约 14–17 倍**；Cycles GPU 相对 CPU 只快约 **16%**。
- 小场景下 Cycles 的时间主要被初始化/内核编译与低采样占用，不能外推到复杂场景。
- A750 oneAPI 路径真实可用，且显存占用约 2.2 GB；8 GB 显存下可运行，但不应与 LLM/TTS/其他 GPU 渲染并发。
- 复杂场景的 GPU 收益需要在 R1 后续用真实 Transformer/工程场景复测。

## 3. Manim

固定 `SmokeScene`，3.8 s 成片；`--disable_caching`，冷启动。

| 模式 | 分辨率 / 帧率 | 耗时 | 产物 |
| --- | --- | --- | --- |
| draft（`-ql`） | 854×480 / 15 fps / 57 帧 | **4.05 s** | `build/r1/benchmark/manim-draft/.../SmokeScene.mp4`（52,896 B） |
| final（`-r 1920,1080 --fps 30`） | 1920×1080 / 30 fps / 114 帧 | **5.38 s** | `build/r1/benchmark/manim-final/.../SmokeScene.mp4`（145,901 B） |

结论：Manim 适合作为数学/算法动画的默认轨道；draft 预览成本低，final 1080p30 也在秒级（小场景）。

## 4. Remotion

固定 `R1Smoke`，1920×1080 / 30 fps / 5.0 s / 150 帧。

| 并发 | 耗时 | 产物 |
| --- | --- | --- |
| 1 | **19.66 s** | `build/r1/benchmark/remotion-c1.mp4`（33,917 B） |
| 4 | **18.59 s** | `build/r1/benchmark/remotion-c4.mp4`（33,917 B） |

结论：小视频下并发 1→4 只快约 5%；Remotion 的主要成本在启动/浏览器与帧渲染，不在编码。长视频/复杂合成需要另行测试。

## 5. FFmpeg 字幕烧录

源：`build/r1/remotion/smoke.mp4`（5.0 s / 1080p30），ASS 双行英中字幕。

| 编码器 | 耗时 | 产物大小 | 结果 |
| --- | --- | --- | --- |
| `h264_qsv -global_quality 20 -preset medium` | **5.34 s** | 44,211 B | pass |
| `libx264 -crf 18 -preset slow` | **2.91 s** | 44,389 B | pass |

结论：

- 5 秒短片上 QSV 反而比 libx264 慢；QSV 的固定启动开销在小文件上占主导。
- 两者产物时长/分辨率/帧率一致；长课程需要复测 QSV 是否有吞吐优势。
- **Windows 路径必须转义**：`ass='D\:/path/file.ass'`，否则 ffmpeg 会把 `D:` 误解析为 `original_size` 选项。本次基准脚本已修正。

## 6. 测量局限（如实记录）

1. Manim / Remotion 的 `peak_process_memory_mb` 只统计主进程，子进程（浏览器/渲染器）未求和，是**下界**。
2. Blender 的进程内存是主进程；Cycles 的 tile/设备 worker 可能在同一进程内。
3. GPU 专用内存计数器包含桌面基线；峰值只能看相对变化，不能当作渲染独占显存。
4. 每个用例只跑一次，没有做多次取中位数；小场景启动开销大，数据只用于选型，不作为 SLA。
5. Blender Cycles 的 CPU/GPU 对比使用 8 samples；真实课程场景需要重新测。
6. FFmpeg QSV 的短片段结论不能直接外推到 20 分钟课程。

## 7. 选型结论

- **Manim**：数学、矩阵、算法、二维结构动画；draft/final 都足够快，适合作为 R1 主动画引擎。
- **Blender**：三维结构、机械、工程可视化；使用 Cycles oneAPI，但小场景收益有限，复杂场景再评估。Eevee 用于快速预览。
- **Remotion**：最终编排、字幕、图文、合成；不重写 Manim/Blender 已完成的动画。
- **Motion Canvas**：保留既有资产；无 headless CLI，不进入 R1 自动化主链路。
