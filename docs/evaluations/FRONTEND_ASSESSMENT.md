# 前端交互必要性评估

> **2026-11-10 更新**：Motion Canvas 已实现无头自动导出（D-054），本文 §1/§3 中"人工导出 / 没有 CLI"的描述已过期；其余关于前端必要性的结论仍按 2026-11-03 的评估保留。

- **日期**：2026-11-03
- **性质**：产品决策评估。本次不开发前端，不引入框架。

## 结论

**当前不开发前端。** 继续使用 CLI + 文件 + 报告。

理由：项目是单机、单用户、以人工节点（Motion Canvas 导出、内容撰写、来源核查）为主的确定性流水线。前端不会减少这些人工步骤，却会新增一套需要与契约、状态、日志保持同步的界面层。

先做一件成本更低、收益更直接的事：**增加只读的 `course-control status --json`（或等价的汇总报告）**，把现有 `build-report.json`、`ModelingStudio/job.json`、`ContentQA/review.json` 聚合成一份状态文件。它是 CLI 的增强，也是未来任何界面的唯一数据源。

**触发开发轻量本地 Web UI（方案 B）的条件**（满足任意两条）：

1. 同时在制的课程 ≥ 3 门，靠目录和终端难以判断各课状态；
2. 人工节点（Motion 导出）被遗漏 ≥ 2 次，且需要主动提醒；
3. 非开发者（编辑、审稿人）需要查看进度与审查结果；
4. 现有报告已经稳定 1 个月以上，字段不再频繁变化。

**明确不做方案 C**：课程编辑、任务调度、可视化剪辑属于另一个产品，成本与维护远超收益。

## 1. 当前使用方式

| 操作 | 现在怎么做 | 产物 |
| --- | --- | --- |
| 建课 | 在 `lessons/<slug>/` 写 4 个文件 + 素材 | 课程契约 |
| 校验 | `course-control validate --lesson <slug>` | 问题列表 |
| 构建 | `build-lesson.ps1 -Lesson <slug>` | `build/<slug>/` |
| 看进度 | 终端输出 + `build/report.json` | stages/checks |
| 看失败 | `build-report.json.failures` + `build/<slug>/logs/*.log` | 日志 |
| 人工导出 | Motion Canvas 编辑器 → 指定文件名 | `animation/<scene>.mp4` |
| 看成片 | 打开 `build/<slug>/final/course-video.mp4` | 视频 |
| 内容审查 | `content-qa review` → `review.md` | 报告 |
| 本地建模 | `modeling-studio run/status` | `workspace/jobs/<job>/` |

特点：所有状态都已经落盘为 JSON/Markdown，终端只是读取入口。

---

## 2. 前端能解决什么

| 问题 | 前端价值 | 现有替代 |
| --- | --- | --- |
| 课程选择与项目创建 | 中 | 建目录即可 |
| 生产进度总览 | **高**（多课程时） | 逐个读 `build-report.json` |
| 各阶段状态与耗时 | 中 | 报告已含 |
| 失败任务与错误信息 | **高**（聚合与定位） | 读 failures + 日志 |
| 人工节点提醒 | **高** | 目前只能靠报告里的 `skipped` |
| 任务恢复/重跑 | 中 | 重跑命令；`--resume` 已存在 |
| 成片与文件查看 | 中 | 打开文件夹/播放器 |
| ContentQA 意见浏览 | **高**（按页、按 verdict 过滤） | `review.md` 可读但不可筛选 |

最适合前端的是**只读聚合**：一屏看到“哪门课卡在哪个阶段、为什么、下一步做什么”。

---

## 3. 前端不能解决什么

- 课程内容质量与事实正确性。
- 本地模型的输出可靠性、幻觉、超时。
- Blender 渲染质量与构图。
- Motion Canvas 的人工导出（没有 CLI，界面也调不动）。
- 在线模型供应商/凭据的可用性。
- 从零生成课程知识。

把这些包装成“点一下就好”的界面，只会掩盖人工节点与外部依赖。

---

## 4. 三种方案比较

| 维度 | A. CLI + 文件（现状） | B. 轻量本地 Web UI（只读 + 少量操作） | C. 完整前端应用 |
| --- | --- | --- | --- |
| 范围 | 现有 | 状态面板、失败详情、人工提醒、报告查看；可选“重跑构建” | 项目管理、编辑器、调度、素材库、可视化 |
| 开发成本 | 0 | 1–2 周（含状态聚合） | 2–3 个月起 |
| 维护成本 | 低 | 低–中（需跟随报告字段） | 高（认证、并发、编辑器、兼容） |
| 使用收益 | 单课足够 | 多课/多人时明显 | 与当前单机单用户不匹配 |
| 架构影响 | 无 | 需要一个只读状态数据源；不改变流水线 | 需要任务队列、持久化、权限、后端服务 |
| 风险 | 无 | 界面与契约漂移 | 范围失控、双套状态 |

### 推荐路径

1. **现在**：保持 A；补一个只读状态聚合（CLI 输出 JSON 或生成静态 HTML 报告）。
2. **满足触发条件后**：做 B，且只做“读”：
   - 课程列表与阶段状态；
   - 失败原因与日志尾部；
   - 人工节点清单（缺哪些导出、缺哪些凭据）；
   - ContentQA 意见按页/verdict 过滤；
   - 有限操作：重跑构建、打开输出目录。
3. **不做 C**：课程编辑与可视化调度不在当前产品边界内。

### 是否需要先增加后端 API

暂不需要独立后端。第一步只需一个**只读聚合命令**，复用已有 JSON：

```text
build/<slug>/final/build-report.json
ModelingStudio/workspace/jobs/<job>/job.json + tasks/*.json
build/<slug>/review/review.json
runtime/tasks/*.json
```

如果未来做 B，再决定是静态页面（每次构建生成）还是本地只读 HTTP 服务；两者都不应改变 PRD 中的流水线契约。

---

## 5. 不做什么

- 不在本期引入 React/Vue/Next 等前端框架。
- 不增加任务调度服务或数据库。
- 不让界面直接调用模型或 Blender。
- 不用界面掩盖 `skipped` / `blocked` / `incomplete`。
