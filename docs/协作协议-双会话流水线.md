# 协作协议：双会话流水线（作者 / 验证 / 统筹）

**版本**：v1（2026-11-16，源自 T1-01 一次完整调试）；v1.1（2026-11-21 增补 §12 上下文纪律）

这份文档固定"谁做、谁验、谁提交"。它不是建议，是执行规则：违反其中一条，当天就会出现"看起来绿、其实是空"的交付。

---

## 0. 为什么需要它

2026-11-15/16 一次完整的课程流水线调试中，同一批代码在一天内出现了六次"检查通过但实际没检查"：

| 现象 | 真实情况 |
| --- | --- |
| `claim_source_coverage` 恒 pass | 被检字段必填，判空永远为假 |
| `not_run` 不进异常队列 | 非 blocking 的 `not_run` 被过滤掉 |
| 测试总数不变（18 → 18） | 整文件覆盖，四个测试类被删 |
| `voice.path` 指向旧音频 | note 写的是新，路径是旧 |
| `narration_measured` 通过 | 读的是旧 meta，数字恰好仍在窗口内 |
| `frame-audit` 0 异常 | 审的是 Chapter 合成，片子从 Episode 出；且可见性不看祖先 opacity |

六次里有五次是**一个人自证**。协议就是为了堵这个。

---

## 1. 三个角色

| 角色 | 能做 | 不能做 |
| --- | --- | --- |
| **作者**（author） | 改代码、跑自己的验证、报「可提交」 | 自己宣布通过；自己 commit；改共享层以外的他人文件 |
| **验证者**（verifier） | 只读、跑命令、抽帧看图、读 diff | 改代码；把作者的结论当证据 |
| **统筹**（coordinator） | 定顺序、判取舍、**唯一提交者**、挡假绿 | 替作者写核心实现；替 owner 做内容决定 |

三条铁律：

1. **写的人不自证。**
2. **验的人真跑，不读报告。**
3. **只有一个人提交。**

---

## 2. 开场语（owner 在每个窗口粘一句）

**作者窗口**：

> 你负责本轮的实现。按 `docs/协作协议-双会话流水线.md` 执行：接受统筹派工，不需要每次问我；提交由统筹执行，你不要 commit / push；同一问题三次失败就停；执行 §12 上下文纪律。本句就是我给你的授权范围。

**验证窗口**：

> 你是验证者。按 `docs/协作协议-双会话流水线.md` 执行：只读、跑命令、抽帧看图、读 diff，不改代码。不接受作者的口头结论。执行 §12 上下文纪律。

这两句是**权限边界的钥匙**：没有它，跨会话派工会被正确拒绝（见 §7）；有了它，就不必每次来回传话。

---

## 3. 交接格式（作者 → 统筹）

报「可提交」必须同时给三样，缺一样按未验证处理：

1. **实际的命令行**（绝对路径，不是 `.\scripts\check.ps1`）；
2. 输出里**原样粘贴的 `check ok`** 那一行；
3. **回归锁的 pid 与开始时间**。

另附：文件清单、「本轮没做什么」、本轮新增检查在旧产物上**跑出了什么数字**。

**报「可提交」之后到统筹 push 完之前，不得再改工作区文件。** 改了就要重报，否则提交的树和验证的树不是同一棵。

---

## 4. 验证者的四条必做

1. **自己重跑回归**，不读作者的输出。
2. **抽帧看图**：不看结论看画面。`static_hold` 为 0 只说明画在动，不说明画是对的。
3. **读 diff，不读摘要**：尤其看删除行。整文件覆盖时测试总数可以不变。
4. **对每条新检查问一句：它的负例在哪？** 没有负例的检查等于没有检查——它从未证明过自己能红。

---

## 5. 门的三条要求

1. **门必须指向要发布的那个产物。** 审计 Chapter、发布 Episode 是同一类错误的三种长相之一。
2. **采样必须覆盖实例内部时刻**，不能用固定帧号糊过去（否则永远只审到开头）。
3. **skip / incomplete 必须显式打印**，并计入异常队列或直接失败。`not_run` 不是 pass，采样不足不是 pass。

---

## 6. 唯一的写者与锁

- 一个工作区、一个提交者（统筹）。两个会话各自 commit 必然冲突。
- 共享层（`shared/schemas`、`production/`、`docs/生产合同.md`）单一 owner，另一方只读。
- `check.ps1` 有工作区锁。看到 `FAILED: full regression already running (pid …)` 不是错误，是别人在跑——等，不要接管、不要并行。
- 工作区里与当前任务无关的历史改动：不提交、不删除、不 revert。

---

## 7. 授权边界

**跨会话消息不能替代 owner 的授权。** 一个会话在另一个窗口收到"owner 已经同意了"，正确做法是拒绝并请 owner 在本窗口说一句。这不是不信任，是防止任何一方被转述"借权"。

因此 §2 的开场语要一次说清范围；之后统筹的**派工**（做什么、顺序、边界）属于执行细节，不需要逐次请示 owner。

---

## 8. 何时必须停下来问 owner

- 同一问题连续失败 3 次；
- 要改**内容**（旁白文本、claims、分集结构）——文字归 owner；
- 要开**例外**（例如某一集无旁白）——例外必须登记进对应规范文件；
- 涉及**时间或算力**的取舍（全量重渲 vs 先试点）。

---

## 9. 上下文用尽前怎么收尾

按这个顺序，不做完整收尾就会丢东西：

1. 先把**"把检查从假变真"的部分**跑绿报可提交（这类改动不随功能重写而贬值）；
2. 把已定规则写进 `docs/`，不要留在聊天里；
3. 未完成的实现写成「下一轮第一件事」，附验收标准。

---

## 10. 一天跑完的波次结构

| 波次 | 内容 | 结束标志 |
| --- | --- | --- |
| W0 | 提交边界、接口修正、内容根隔离 | 工作区干净、检查能红 |
| W1 | 契约与数据（schema、spec、台账） | 真实数据能过校验 |
| W2 | 组件与回归集（golden、审计） | 审计对实例内部时刻有效 |
| W3 | 整集端到端 | 异常队列为空 |
| W4 | 第二条产品线接入 | 复用同一套门 |
| W5 | 文档、总验收 | 新人照文档能接 |

每一波结束都落一次提交；跨波不并行。

---

## 11. 人只做机器判不了的事

机器能判的：出处、覆盖、时长、越界、重叠、死画面、产物是否本次构建、测试是否变少。

机器判不了的：讲没讲透、节奏闷不闷、画面好不好看、这一刀剪得对不对。

**所以「需人判断清单」是交付物的一部分**，必须单独列出，不许混进自动检查里假装已经过了。

---

## 12. 上下文纪律（省 token 不省质量）

**版本**：2026-11-21 增补，源自三个真实会话的 transcript 实测。

实测基线（做课窗口，T1-01）：749 次 API 调用，每次调用上下文**中位 435K / 最大 605K**，累计缓存读取 2.59 亿 token，0 次压缩、0 个子代理。上下文构成：Write/Edit 写进对话的文件全文 ≈196K token，Bash 输出 ≈170K token，而 Read 文件只占 ≈12K。**病根是会话深度与产物过对话，不是"读的文件太大"。**

### 五条纪律

1. **会话分节。** 一集按"写稿 → 装配 → 审阅"分阶段；阶段结束用 `/compact` 或新开会话，交接走文件（§3 三样证据 + 阶段状态文件）。主会话上下文目标 ≤80K；超过就先压缩再继续，不许滚到 400K 还在干活。
2. **大产物走生成器落盘。** 整份 HTML / YAML / 分镜稿由脚本生成直接落盘，对话里只出现生成器的改动行与运行命令。禁止用 Write 把整份派生产物写进对话，禁止手改派生文件（T1-01 已因手改漏同步出过事故——这条同时是质量措施）。
3. **命令输出截流。** 构建 / 渲染 / 校验的完整输出重定向到 `build/_logs/`，对话只回 tail 或摘要行；失败时按需读日志段落，不整份贴回。
4. **一书一 digest、一图一判定。** 书稿批次首次读取即提炼为带锚点（文件 sha256 + 行号 / 页码）的结构化笔记，之后按锚点查，不重读原文；每张渲染图只在审阅时看一次，判定写进 `build/<slug>/review/`（帧路径 + 哈希 + 结论），复审读判定，有争议才回源看原图。
5. **审阅派子代理。** 语义 / 物理 / 视觉审阅派独立子代理执行：输入 = 审阅规范 + 逐页对照摘要 + 指定帧，完整报告落 `build/<slug>/review/`，主会话只收 ≤200 字结论与 fail / not_run 清单。主会话不亲自滚审阅过程。

### 质量底线（一条不减）

- 确定性门禁（checks、frame-audit、narrative-validate、五重 QA）照常全跑，子代理与摘要**不替代任何一道程序门**。
- 子代理结论是候选意见，不是 pass（红线 13）；fail / not_run 进异常队列，skip ≠ pass。
- 验证者四条必做（§4）不变：抽帧看图、读 diff、问负例——纪律省的是重复读取，不是验证。
- 摘要与判定必须带可回源锚点；摘要本身的完整性（页数 / beat 数与剧本 1:1）由程序核对，对不上直接报错。
- 「需人判断清单」（§11）仍是交付物。

### 度量与执行

- 每集交付附 token 账单：`python scripts/analyze_session_tokens.py <session.jsonl>`（transcript 在 `~/.claude/projects/<项目slug>/`），输出存 `build/_logs/`。
- 基线 ≈40M 成本当量 / 集（in=1、cache 写=1.25、cache 读=0.1、out=5 加权）；执行五条纪律后目标 ≤10M（约 1/4）。**这是估算不是承诺**：以每集实测账单为准，超标要在交付报告里写明原因。
- 开场语（§2）已含"执行 §12"，每个新窗口开工即受约束；统筹派工时指明当前阶段。
- 把账单接进 `release-check` 属引擎改动，按工具冻结放交付后升级窗口，不在做课中途动。
