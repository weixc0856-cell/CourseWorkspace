## 1. 结论

1. **路线成立，可以有条件进入 E0 + E1。** 本机已具备 VS Code 1.145.1、WSL2 Ubuntu 24.04、Docker 29.9.1、Rust 1.97、uv、ffmpeg gdigrab；shell、Python、Rust 都能真实执行。
2. **必须先补 E0 契约，再写 E1。** 否则会先得到一个“能录屏但证明不了执行”的脚本，后面再补 `session_id`、证据清单、失败分类与缓存，返工成本更高。
3. **证据分三条，不能合并**：
   - 机器证据：退出码 + 分离的 stdout/stderr + 断言结果；
   - 终端记录：PTY transcript（含 ANSI 与交互）；
   - 视觉证据：mp4。
   `script` 记录的是终端会话，**不区分 stdout/stderr**；因此机器证据必须由执行监督程序单独采集，不能拿 PTY 日志冒充。
4. **VS Code 的可靠主路径是 Shell Integration API**：`executeCommand` + `read()` + `exitCode` / `onDidEndTerminalShellExecution`。但 `read()` 必须立即调用，`exitCode === undefined` 必须判失败；没有 shell integration 时 `sendText` 只能做降级展示，**不能作为执行证据**。
5. **Docker 可以承担“规范执行环境”，但不是无条件安全沙箱**。必须固定 digest、非 root、只读根文件系统、drop capabilities、no-new-privileges、资源限制、默认断网、最小挂载；`sudo` 只出现在专门的权限实验镜像里。
6. **录屏成功 ≠ 执行正确 ≠ 课程目标达成。** 三个层次必须分别有断言；只断言退出码 0 不够。
7. **Manim 是渲染引擎，不是生产系统。** 最终仍由 FFmpeg/Remotion/剪辑时间轴承担合成、配音与字幕。

## 3. 三条证据链

| 证据 | 生产者 | 内容 | 用途 |
| --- | --- | --- | --- |
| **机器证据** `result.json` | 执行监督程序（容器内 runner） | 退出码、分离的 stdout/stderr、断言结果、耗时、镜像 digest、工具版本 | **唯一正确性依据** |
| **终端记录** `session.cast` / `session.log` | PTY / `script` / VS Code `read()` | 含 ANSI、回显、交互、时间信息 | 交互复现、诊断、展示 |
| **视觉证据** `session.mp4` | ffmpeg gdigrab | 实际窗口/桌面画面 | 展示与审看；**不证明正确性** |

关联方式：同一个 `session_id` + 同一个 `shot_id`，由 `EvidenceManifest` 把三者绑定。禁止用视频哈希证明程序正确，也禁止用 `script` 日志代替 stdout/stderr。

### 3.1 执行监督程序

容器内运行一个 `session-runner`，而不是直接 `bash session.sh`：

```text
session-runner
  ├─ 读取 SessionSpec
  ├─ 逐条执行命令（subprocess，stdout=PIPE，stderr=PIPE）
  ├─ 把输出同时写回终端（供录屏查看）
  ├─ 写 result.json（分离流、退出码、断言）
  └─ 写 transcript（可选，供交互诊断）
```

这样：

- 屏幕上是真实输出，`result.json` 是同一进程的真实流；
- stdout/stderr 不依赖 PTY 合并；
- VS Code 的 `read()` 只用于交互展示与 transcript，不作为机器证据。

## 4. 执行状态机与失败分类

```text
PREPARE ──环境/镜像/素材/窗口检查──┐
   │ 失败                          │
   ▼                               ▼
ENVIRONMENT_FAILED            EXECUTE + RECORD
                                   │
                                   ├─ 命令失败/断言失败 → ASSERTION_FAILED / EXECUTION_FAILED
                                   ├─ 超时 → TIMEOUT
                                   ├─ 录屏失败 → RECORDING_FAILED
                                   └─ 证据缺失 → EVIDENCE_INCOMPLETE
                                   ▼
                                VERIFY
                                   │
                                   ▼
                          PASS → collect → compose
```

失败分类（写进报告，不允许只写 fail）：

| 代码 | 含义 |
| --- | --- |
| `ENVIRONMENT_FAILED` | 镜像拉取、容器启动、工具链、窗口/DPI 检查失败 |
| `EXECUTION_FAILED` | 命令非零退出、崩溃、信号终止 |
| `ASSERTION_FAILED` | 退出码符合但 stdout/文件/状态断言不符 |
| `RECORDING_FAILED` | gdigrab 未启动、窗口不存在、ffprobe 失败 |
| `EVIDENCE_INCOMPLETE` | 缺 result.json、缺 transcript、缺视频，或 VS Code exit code 为 undefined |
| `TIMEOUT` | 命令或会话超时，容器已被终止 |

原则：

- 录屏失败不等于执行失败；执行失败也不等于录屏失败，报告要分开。
- 任何 `EVIDENCE_INCOMPLETE` 都不得记成 `pass`。
- 失败时保留容器日志、窗口截图、`result.json`、`session.cast`、ffmpeg 日志。

## 6. 执行环境：Docker 基线

### 6.1 推荐运行参数

```bash
docker run --rm \
  --user course \
  --read-only --tmpfs /tmp:rw,noexec,nosuid,size=256m \
  --cap-drop ALL \
  --security-opt no-new-privileges \
  --pids-limit 256 \
  --memory 2g --cpus 2 \
  --network none \
  -v <lesson-assets>:/mnt/lesson:ro \
  -v <work-volume>:/work:rw \
  course-tools@sha256:...
```

- 镜像按 digest 固定；容器 `--rm`；工作卷单独创建并清理。
- 不挂载宿主 home、不挂载 Docker socket、不使用 `--privileged`。
- 默认断网；需要 pip/uv 的课程单独授权 `--network bridge`，并记录到 `ExecutionResult.environment.network`。
- `sudo` 不进入通用镜像。权限实验使用单独的 `course-tools-sudo` 镜像，且只挂载专用工作卷。
- 图形/GPU 课程单独评估，不默认加 `--gpus`。

### 6.2 镜像分层

| 镜像 | 内容 | 用途 |
| --- | --- | --- |
| `course-tools:base` | bash、coreutils、findutils、grep、sed、awk、tmux、vim、python3、uv | shell / Python 基础 |
| `course-tools:rust` | base + rustup/cargo | Rust |
| `course-tools:sudo` | base + 受控 sudoers | 权限实验专用 |
| `course-tools:net` | base + curl/ssh 客户端 + 本地测试服务 | 网络演示专用 |

### 6.3 Docker Desktop vs Docker Engine in WSL2 vs 纯 WSL2

| 方案 | 优点 | 代价 | 结论 |
| --- | --- | --- | --- |
| Docker Desktop（当前） | 已安装 29.9.1；Dev Containers 开箱可用；从 Windows 直接录终端 | Desktop 许可；GUI/VM 开销；WSL 集成当前未开启 | **E1/E2 先用它** |
| Docker Engine in WSL2 | 无 Desktop 许可；原生 Linux docker；WSL 内直接跑容器 | 需 systemd、cgroup v2、iptables/nftables；VS Code 需配置 docker host；维护成本 | **评估项**：E3 前用同一 E1 会话跑一遍对比 |
| 纯 WSL2（日常发行版） | 最轻；bash/python/uv/cargo/tmux 已齐 | 不是隔离；共享宿主状态；不可复现 | **只做开发调试**，不做规范证据 |

决策门：同一个 E1 session 分别在 Docker Desktop 与 Docker Engine in WSL2 下执行，比较以下指标，结果落盘后再决定是否迁移：

| 指标 | 怎么测 |
| --- | --- |
| 冷启动 | 从 `docker run` 到容器 ready 的秒数 |
| 录制稳定性 | 连续 5 次录制，窗口/终端是否掉帧、黑屏、焦点丢失 |
| Dev Container | VS Code 打开同一 compose/devcontainer 的成功率与耗时 |
| 清理残留 | 结束后的容器、卷、镜像层、端口占用 |
| 资源 | 空闲内存、CPU 占用、磁盘增长 |
| 许可 | Docker Desktop 是否覆盖使用场景（已确认当前可用） |

Docker Engine in WSL2 的迁移检查（只记录，不在本评估实施）：`/etc/wsl.conf` 开启 systemd；安装 docker-ce；用户加入 docker 组；`docker context` 指向 WSL 内 socket；VS Code 通过 Remote-WSL + `docker.host` 或 Dev Containers 连接；Windows Terminal 录制 `wsl → docker run -it`。

结论：

- E1/E2 用 Docker Desktop。
- E3 前完成对比；若 Engine in WSL2 在稳定性/清理/许可上不劣，迁移为规范环境。
- 纯日常 WSL2 只做开发调试，不进入证据链。
- 长期目标：Docker Engine in WSL2 承担规范执行；WSL2 承担开发与交互式讲解；两者都不宣称是安全沙箱。

### 6.4 WSL 的定位

WSL 继续作为开发、调试和日常工具链环境；**规范执行与验证以 Docker 为准**。原因：镜像可固定、资源可限制、生命周期可清理、证据可关联；WSL 是共享的宿主状态，不适合作为最终证据环境。

## 7. VS Code 实操

### 7.1 主路径

```text
window.onDidChangeTerminalShellIntegration
  → shellIntegration.executeCommand(...)
  → execution.read()        // 立即调用，否则丢失开头
  → execution.exitCode      // Promise
  → window.onDidEndTerminalShellExecution // exitCode: number | undefined
```

规则：

1. `read()` 必须在 `executeCommand` 后立即调用；只用于 transcript，不作为 stdout/stderr 证据。
2. `exitCode === undefined` → `EVIDENCE_INCOMPLETE`，不得视为成功。
3. `executeCommand` 抛错（task terminal 等）→ 降级 `sendText`，但该镜头只能标记 `EVIDENCE_INCOMPLETE`，除非容器内 runner 同时提供了完整机器证据。
4. Shell Integration 3 秒内未激活 → 记录能力检测失败，进入降级路径。
5. 机器证据仍以容器内 `session-runner` 的 `result.json` 为准；VS Code 只负责“被录制的那个终端”和交互。
6. 扩展要捕获 `onDidEndTerminalShellExecution` 的事件对象，按 `execution` 身份匹配，避免多个终端串扰。

### 7.2 隔离配置

- `--user-data-dir`、`--extensions-dir` 指向 `build/<slug>/code/<shot>/`。
- 固定设置：主题、字号、`window.zoomLevel`、关闭通知/更新/平滑滚动、`editor.cursorBlinking: solid`、`window.title` 固定。
- 目标环境：Dev Container 或 Remote-WSL；VS Code 只作为窗口，命令在容器内执行。
- 扩展只做“演示驱动”，不承担唯一证据来源；它的代码要进仓库并受测试。

### 7.3 录制

- `ffmpeg -f gdigrab -i title=<固定标题>` 或 `hwnd=<句柄>`；E1 先实测 `title`/`hwnd` 在本机是否稳定。
- 窗口位置不必固定（按标题/句柄捕获），但**客户区尺寸、DPI 缩放、面板布局、字号**必须固定。
- 录制前检查窗口存在、尺寸正确；录制后 ffprobe 检查时长/帧数/分辨率/文件完整性。
- GPU 加速窗口（部分图形程序）可能无法被 gdigrab 正确捕获；图形课程必须单独实测，必要时改用 OBS/Windows Graphics Capture。
- 默认 1920×1080@30；需要 1440p/4K 时按“原生分辨率采集 → 高质量中间文件 → 目标分辨率编码”，不先录 1080p 再放大。

## 8. 课程级断言（不只 exit code）

每个命令除退出码外，还可以声明：

| 断言 | 示例 |
| --- | --- |
| `stdout` / `stderr` | 精确文本或正则 |
| `files` | 产物存在、大小、哈希 |
| `state` | `test -d .venv`、`stat -c %a`、`uv pip list` 包含某包 |
| `environment` | `which python` 指向 `.venv/bin/python` |

示例：venv 课程如果只打印 `Hello World`，退出码 0 也不能证明“虚拟环境隔离”达成；必须断言 `.venv` 存在、`which python` 在 `.venv` 内、依赖只装在该环境。

## 9. 轨道划分与动画

| 轨道 | 适用 | 生产工具 |
| --- | --- | --- |
| 终端实操 | shell、vim、tmux、ssh、权限 | Docker + PTY + ffmpeg |
| VS Code 编程 | Python、Rust、图形编程 | CourseDemo 扩展 + Dev Container + ffmpeg |
| 数学动画 | 3B1B、Reducible | Manim（渲染引擎） |

Manim 只负责场景；配音、字幕、剪辑、最终编码仍由现有 Remotion/FFmpeg 轨道承担。不要把它做成第二套生产系统。

### 9.1 复刻基准

- **技术基准：FFT（Reducible）**。数学结构集中，适合验证 Manim 场景管理、公式、时间轴、镜头切换、输出。
- **产品基准：Transformer（3B1B）**。作为“完成度高”的参照，验证复杂概念拆解与动画编排。
- “完全复刻”定义为：讲解结构、构图语法、动画节奏、配色与镜头语言对齐；不逐帧复制，不复制原片脚本、旁白与音轨。来源与版权要记录。

## 10. 语音接入（VoxCPM2）

### 10.1 运行时实测

| 项 | 值 |
| --- | --- |
| 服务 | `D:\AI\VoxCPM-Runtime`，FastAPI，`127.0.0.1:50000` |
| 模型 | VoxCPM2（`model.safetensors` 4.58 GB + `audiovae.pth` 0.38 GB） |
| 设备 | **CPU-only**，约 6 GB 内存，不占 A750 |
| 输出 | 48 kHz / 16-bit PCM / 单声道 WAV |
| 加载 | 23–29 秒到 `ready`；期间 `/health` 返回 `loading` |
| 速度 | RTF ≈ 9–12.5；2 分钟旁白约 18–24 分钟 CPU 时间 |
| 音色 | **没有预置音色**；`/speakers` 恒为空；必须提供参考 WAV（+ 可选逐字文本） |
| 随机性 | 无固定种子；同一句多次合成长度会波动（实测 3.2–3.5 s） |
| 许可 | Apache-2.0；允许商用；禁止冒充他人；AI 生成内容应标注 |

接口：

```text
GET  /health          -> status: ready | loading
GET  /speakers        -> []
POST /tts             -> JSON {text, prompt_wav?, prompt_text?, reference_wav?, speed?, text_frontend?}
POST /tts/upload      -> multipart
响应 audio/wav，头：X-Audio-Seconds / X-Synth-Seconds / X-Sample-Rate / X-Prompt-Mode / X-Text-Normalize / X-Speed-Stretch
```

约束：

- 请求必须带 `prompt_wav`（或配置默认 `VOX_PROMPT_WAV`）；缺参考音返回 400。
- 调用方超时不要低于 600 秒。
- 本机 http 调用必须忽略系统代理（`trust_env=False` 或 `ProxyHandler({})`）。
- 50000 同一时刻只允许一个运行时；谁启动谁停止；空闲时端口应为空。

### 10.2 时间线：Session 先录后配，Manim 先配后渲

语音不是后期叠加，但两条轨道的先后不同：

**Session / 终端 / 代码轨道：先录制，后配音。**

```text
session 规格（命令、trim 规则）
  → 真实执行 + 录制
  → 应用等待剪辑（cut）
  → 实测最终时长
  → VoxCPM2 合成旁白（按最终时长写文本）
  → 合成旁白与字幕
```

原因：联网安装、命令等待、编译时间只有执行后才知道；先切掉等待，旁白才不会描述一段被剪掉的空白。

**Manim 轨道：先配音，后渲染。**

```text
逐字稿 → TTS 片段 → 实测时长 → 场景时长/镜头节奏 → 渲染
```

规则：

1. **页面预算仍是上限**。片段超出页面预算 → `NARRATION_OVERFLOW`，由作者改文本或改预算；程序不改正文。
2. **片段起点对齐页面起点**；拼接时用静音补齐到时间线总长，保持 V-15 的音频/视频时长检查不变。
3. **代码镜头**：录制并剪辑后的最终时长决定旁白文本预算；旁白片段长于该镜头 → `NARRATION_OVERFLOW`，不静音裁切。
4. 默认 `speed=1.0`；不靠变速适配时长，变速是后处理，音质与原生不等价。
5. 没有固定种子：必须实测每段时长并记录，不能按字数估算。

### 10.3 `narrate` 接入设计

```text
course-control narrate --lesson <slug> [--no-start-service] [--only slide-003]
```

- 逐页从 `lecture_notes.md` 的“逐字口播”提取文本（人审后使用）。
- 输出：`build/<slug>/narration/segments/slide-001.wav`、`narration.wav`、`narration.meta.json`。
- 缓存键：`sha256(text + voice_ref_sha + prompt_text_sha + model/version + timesteps + cfg + text_frontend + speed)`；命中则复用，并在 meta 中标记 `cache_hit`。
- 参考音：已确认 `D:\Local-Drama-Studio\assets\audio\prompts\my_voice_clean_v1.wav`（24 kHz / 单声道 / 3.37 s）；逐字文本已确认是“希望你以后能够做的比我还好呦。”。没有同名 `.txt`，直接写入 `config/local-paths.yaml` 的 `tts.prompt_text`，不提交到仓库。
- 配置在 `config/local-paths.yaml`（已忽略）：

```yaml
tts:
  base_url: "http://127.0.0.1:50000"
  voice_ref: "D:/Local-Drama-Studio/assets/audio/prompts/my_voice_clean_v1.wav"
  prompt_text: "希望你以后能够做的比我还好呦。"
  auto_start: true
  wait_timeout_s: 1800
  timesteps: 10
```

- 服务生命周期（自动 + 等待 + 可查询）：
  - 先取 `runtime/locks/tts-50000.lock`；锁内容记录 `task_id`、PID、host、`mode`（started/reused）、`since`。
  - 取锁等待时每 10 秒打印占用人：`TTS 50000 busy: task=<...> pid=<...> since=<...>; waiting`；超时返回 `TTS_BUSY`，不 kill 他人进程。
  - `/health == ready`：复用，不停止，`mode=reused`。
  - `loading`：等待至多 120 秒。
  - 未监听且 `auto_start=true`：由 `narrate` 启动运行时（venv 的 `python api_server.py`，固定 env），记录 PID；任务结束只停止自己启动的实例。
  - 未监听且 `auto_start=false`：`TTS_UNAVAILABLE`。
  - 外部程序占用 50000 且未持本锁：`tts-status` 显示端口 PID/进程路径，并标注“external, not started by CourseControl”；`narrate` 仍可复用 ready 服务，但无法得知对方任务。
  - 端口被占用但 `/health` 不健康：等待至多 120 秒；仍不健康返回 `TTS_BUSY`，**不新起第二个实例**。
  - 自动启动的日志写到 `build/<slug>/narration/tts-server.log`，不写 `<AI_ROOT>`。
  - 局限：如果外部调用方既不持本锁、也不暴露任务信息，OS 只能看到 50000 的服务进程，无法知道“具体是哪个程序在调用”；要让状态完整，外部程序需复用同一锁或写入共享状态文件。
- 跨项目约定：建议本机其他课程工具（如 Local-Drama-Studio）复用 `runtime/locks/tts-50000.lock` 的字段约定；否则只能看到服务进程，无法知道具体调用方。
- 状态查询：`course-control tts-status` 输出 health、端口 PID/进程、锁持有者、model、sample_rate、timesteps。示例：

```text
TTS 50000: ready
model: VoxCPM2, sample_rate=48000
port owner: python.exe pid=1234 (D:\AI\VoxCPM-Runtime\.venv\Scripts\python.exe)
lock: task=course:01-shell:V1 pid=5678 since=2026-11-06T15:12:00 mode=started
timesteps: 10 (final only)
```

其他程序调用时，至少能回答“现在是谁在用 50000”。

- 调试与成品：
  - **V1 只做 final**：固定 `timesteps=10`，不引入 draft profile、不做服务配置切换。
  - 调试效率靠 `--only <page>`、片段缓存、跳过未改页；不改服务参数。
  - meta 与报告记录 `timesteps=10` 与 `cache_hit`；没有 draft 产物。
- 失败分类：`TTS_UNAVAILABLE`、`TTS_BUSY`、`TTS_TIMEOUT`、`NARRATION_OVERFLOW`、`NARRATION_MISMATCH`。
- 新增 V-25：`narration.meta.json` 完整、片段哈希与文本匹配、累加时长不越页；V-15 继续检查成片音频。

### 10.4 许可、音色与合规

- VoxCPM 代码与模型为 **Apache-2.0**，允许商用；但仍禁止冒充他人、欺诈与虚假信息。
- 参考音必须是作者本人或已获授权的声音；参考音与逐字文本放仓库外或本机忽略配置，不进版本库。

### 10.5 联网演示、离线验证与等待剪辑

Python 课程采用“联网演示 + 离线验证”：

1. **联网演示**：容器 `network: bridge`，固定包版本，优先 `--find-links` 本地 wheelhouse；`result.json` 记录完整执行。
2. **离线验证**：安装写入 `/work/.venv`（bind mount / 命名卷），随后启动 `network: none` 的第二个容器，挂同一 `/work`，执行断言（`which python`、`pip list`、导入、运行）。证明产物不依赖网络。
3. **等待剪辑**：session 规格为命令声明 `trim`：
   - `trim: {command: c1, keep_head_s: 2, keep_tail_s: 2}`：剪掉中间等待，插入 2 秒“安装依赖…”标题卡；
   - 或 `trim: {max_wait_s: 5}`：等待超过 5 秒的部分压缩成标题卡。
   - 剪辑只影响视频，`result.json` 仍记录完整执行；最终时长 = 录制时长 - 剪掉时长 + 标题卡时长。
4. **次序**：Session 轨道先录制、再剪辑、再按最终时长合成旁白；Manim 轨道仍先配音。
5. **证据**：联网会话与离线会话各自生成 `result.json`；视频只用联网会话（带剪辑），离线会话作为独立证据；两个 `session_id` 都写入 EvidenceManifest。
6. **venv 持久化**：安装写入 `/work/.venv`（bind mount / 命名卷）；离线容器 `--network none` 挂同一目录；不要用 `--rm` 丢掉环境。
7. **命令断言**：`which python` 指向 `/work/.venv/bin/python`；`pip list` 版本固定；导入/运行通过。
5. 新增失败码：`NETWORK_REQUIRED`、`OFFLINE_VERIFY_FAILED`、`WAIT_TRIM_INVALID`。

### 10.6 与 session 的先后

- E1 先用**静音**终端会话证明执行/录制/熔断链路；不把 TTS 的 9–12 倍耗时绑进第一版。
- V1 接入 `narrate`，用真实旁白驱动 session 节奏。
- E2 再做 VS Code + 旁白；避免同时调试录屏、shell integration 与 TTS。

## 13. 与原方案的关键修正

| 原方案 | v3 |
