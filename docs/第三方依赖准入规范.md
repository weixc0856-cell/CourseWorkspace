# 第三方依赖准入规范

本规范约束“什么时候可以引入外部实现、引入前要核什么、引入后怎么维护”。
它适用于代码依赖（npm / PyPI / vendored 源码）、模型权重、字体、音频与素材。

## 1. 原则

1. **先找轮子。** 能由成熟实现完成的，不自己写。自写只用于：确实没有对应实现、许可证不兼容、或外部实现与本项目的数据契约冲突并有实测证据。
2. **不盲目引入。** 每个新依赖都要留下评估记录；**引入后产生负面效果的，pass 掉**，不以“别人都在用”作为理由留在流水线里。
3. **负面效果一票否决。** 至少覆盖：性能回退、产物不可确定性复现、许可污染、离线不可用、维护停滞、与既有版本契约冲突。
4. **更新要及时。** 依赖不是一次性决定；每次迭代开始时校核上游是否更新，落后要做取舍并记录。

## 2. 准入检查表

引入前逐项填写，结果写进 `docs/DECISIONS.md` 或本文件的登记表：

| 项 | 要求 |
| --- | --- |
| 上游身份 | 明确的仓库 URL 与发布渠道；不使用来历不明的镜像或二次打包 |
| 许可 | SPDX 标识；是否允许商用；是否与 AGPL-3.0-or-later 兼容；需要时补 `NOTICE` |
| 口碑 | GitHub star / fork / open issues；是否有真实使用方与 issue 响应 |
| 维护活跃 | 最近 push 与最近 release 时间；近 6 个月无发布视为停滞，需要说明 |
| 版本一致性 | 与项目已锁定版本对齐（例：three 核心与 addons 必须同一版本） |
| 负面效果 | 性能、体积、确定性、离线能力、可复现性逐项实测，不以估算代替 |
| 记录 | 版本号、来源、校核日期、接受/拒绝理由 |

取数命令（结果必须带日期写进登记表）：

```powershell
gh api repos/<org>/<repo> --jq '{stars:.stargazers_count, forks:.forks_count, open_issues:.open_issues_count, pushed:.pushed_at, license:.license.spdx_id}'
npm view <pkg> version time.modified
```

## 3. 更新节奏

- **每次迭代开始**：对登记表里的每个依赖跑一次取数命令；上游有新版本就记录差距。
- **落后 ≥ 2 个 minor 版本**：必须开升级任务，或在决策记录里写明暂不升级的原因与风险。
- **升级前**：先跑该依赖的等价回归（本项目的 `check.ps1` + 相关镜头的 `VERIFY.md` 复核），不能只看编译通过。
- **升级后**：更新登记表与 `NOTICE`（许可变化时）。

### 4.1 three.js 说明

- **为什么现在锁 r160**：`CodeVideoStudio/shots/primer-aging/three.module.js` 早已按 r160 vendored；addons 必须与核心同版本，否则 `EffectComposer`/`BokehPass` 的 API 与着色器契约不匹配。
- **差距**：上游最新 0.187.0，本地落后 27 个 minor。升级需要同步替换核心 + addons，并重跑镜头 `VERIFY.md`（真实渲染、确定性哈希、成片 QC）。
- **当前处置**：本轮只补 addons，保持 r160 自洽；升级列为 P1 待办，未完成前不得把“已是最新”写进任何报告。
