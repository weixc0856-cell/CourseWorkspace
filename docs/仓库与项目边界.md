# 仓库与项目的边界

- **日期**：2026-11-12
- **状态**：现行。2026-11-12 按此边界完成一次迁移。
- **检查命令**：`course-control separation`

---

## 1. 一条规则

**仓库是工具，内容根是项目。**

程序仓库（CourseWorkspace）只回答"怎么做课"：代码、契约、Schema、测试夹具、可复用规范、决策记录。
内容根（`<内容根>`）负责"这门课是什么"：某一系列的方案、研究、证据和产物。

课程开发（造工具）和实际开发课程（做某门课）是两件事。新闻之类的项目同理，也是内容根下的一个项目，不因为它们"不是课程"就另开一套结构。

## 2. 三层

| 层 | 位置 | 进仓库 | 内容 |
| --- | --- | --- | --- |
| 程序 | `CourseWorkspace/` | 是 | `CourseControl/` 及各引擎、`shared/`、`scripts/`、`docs/`、`config/*.example.yaml`、`tests/fixtures/` |
| 项目 | `<内容根>/projects/<系列>/` | 否 | 生产方向、分集方案、研究、评审纪要、领域术语 |
| 产物 | `<内容根>/{lessons,engines,audio,build,deliver,runtime,knowledge}/` | 否 | 课程正文、场景、声音资产、构建、交付、教材 |

`<内容根>/archive/` 是第四类：**已经结束的事**。一次性报告、证据、旧方案放这里，只读不改。

## 3. 内容根长什么样

```text
<内容根>/
├── lessons/            课程正文与契约（唯一的课程输入）
├── engines/            课程场景：manim/、blender/{scenes,tasks}/、code_video/shots/、motion_canvas/scenes/
├── audio/              voice-bibles/、lexicons/
├── references/         参考库：对标影片记录、Golden Sample 哈希
├── projects/           各系列项目材料（见 §4）
├── archive/            历史记录
├── knowledge/          教材区
├── build/              生成物，可删可重建
├── deliver/            最终交付
└── runtime/            锁与任务记录
```

## 4. 新开一个项目

```text
<内容根>/projects/<系列>/
├── README.md           这个系列是什么、目标观众、集数预算（可选）
├── 生产方向.md         定位、边界、参考对标
├── plans/              分集方案、大纲、集间边界
├── research/           来源、数据、行业资料（可链接 knowledge/）
├── reviews/            评审纪要、外部意见
└── evidence/           该项目的验收证据、截图、报告
```

不必一次建齐；用到哪个建哪个。约定只有两条：

- **同名原则**：项目目录名 = 系列 slug（与 `lessons/<slug>` 的系列前缀一致即可，如 `automotive-aerodynamics` 对应 `a01-...`、`b01-...`）。
- **结论上浮**：项目里的通用方法（能复用到别的系列）提炼成仓库 `docs/` 下的规范；过程文件和一次性结论留在项目里。

## 5. 什么绝不进仓库

- 课程正文：`slides.md`、`lecture_notes.md`、`outline.md`、`storyboard.yaml`
- 场景与任务：`engines/**`、`BlenderStudio/tasks/<课程>/`
- 声音：参考音频、旁白 wav、`audio/voice-bibles`、`audio/lexicons`
- 项目材料：`projects/**`、`archive/**`
- 产物：`build/`、`deliver/`、`runtime/`、media 文件
- 教材：`knowledge/`、PDF、Docling 输出

## 6. 什么可以留在仓库

只有两类：

1. **测试夹具**——名字像课程，实质是测试数据。白名单在 `CourseControl/src/course_control/separation.py: ALLOWED`，**2026-11-12 起为空**：最后三个课程形状的目录（两份 Blender 任务目录、一个 Motion Canvas 场景目录）都移到了内容根，仓库只剩 junction。
2. **可复用的方法**——从项目里提炼过、不带具体课程内容的规范，放 `docs/`。

新增白名单必须在 `ALLOWED` 里写明理由，不允许只加路径。

## 7. 怎么检查

```powershell
course-control separation            # 列出仓库里与课程同名的目录
course-control separation --json     # 机器可读
```

输出每一处命中，标注 `allowed` 或 `PROBLEM` 与理由；有 `PROBLEM` 时退出码 1。

- 目录 junction / 符号链接会被跳过：路径在仓库里，字节不在。
- **切换分支的坑**：如果某个历史提交仍跟踪着这些路径，`git checkout` 会把文件写回工作区，覆盖 junction 指向的内容。2026-11-12 合并时踩过一次（Motion Canvas 场景被清空，从 `b8eb450` 恢复）。需要看旧提交时用 `git worktree`，不要在同一个工作区来回 checkout。
- 内容根等于工作区（干净克隆、未配置 `content_root`）时检查自动关闭，不会误报。
- 同一命令还会提示 `docs/` 下的非文稿数据（Markdown / YAML 与 `docs/contracts/` 之外的文件）：那是警告，不阻断，但每一份都该有留下的理由。

## 8. 归档怎么用

`<内容根>/archive/` 里的东西**不再参与检查**，也不再是指令。它的用途只有一个：写新规范时能查回当时的依据。

提炼的方向是逆向的：读到一份旧报告 → 找出仍然成立的结论 → 写进 `docs/` 的规范或决策 → 报告本身继续留在 archive。不要把 archive 原样搬进 `docs/`，那只是换个地方堆文件。
