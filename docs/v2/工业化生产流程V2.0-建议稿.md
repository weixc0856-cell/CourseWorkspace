这项工作的候选名称是 CourseWorkspace 工业化生产流程 V2.0。目标不是增加一批审批表、配置文件和命令，而是建立一条能够持续生产高质量课程的完整生产线。

这次执行分成两个完全独立的交付项目：

1. CourseControl（程序项目）：负责生产工具、数据结构、自动化、版本管理、质量检查和交付管理。
2. CourseContent（课程项目）：负责教材研究、知识组织、讲稿、分镜、动画、旁白、剪辑和最终课程。

两个项目通过稳定的接口协作，但课程内容不反向污染生产工具，生产工具的实现也不成为课程内容的质量标准。

## 一、先确定工业化原则

整个生产体系采用一个核心原则：

以交付质量作为唯一最终验收标准，时间、镜头数量、动画数量、制作时长均不是质量闸门。

例如：

- 20 分钟课程可以有 30 个镜头，也可以有 100 个镜头。
- 某个概念可能用一张静态图讲得最好，也可能需要完整的三维演示。
- Animatic 可以反复修改，不因修改次数而判定失败。
- 旁白可以重新录制，画面也可以重新制作。
- Picture Lock 和 Dialogue Lock 是版本管理机制，不是禁止修改的行政规定。修改后重新验证下游依赖即可。

最终验收只看三个核心方面：

| 质量维度 | 验收问题 |
| --- | --- |
| 内容质量 | 是否把问题讲明白？知识、证据、逻辑是否可靠？ |
| 视觉质量 | 关闭旁白后，画面是否仍然具有完整的设计、过程和表达目的？ |
| 交付质量 | 音画、字幕、技术参数、文件和版权信息是否达到发布标准？ |

这三个方面全部通过，才算完成。

## 二、现有系统盘点：保留什么，改造什么

已检查 `weixc0856-cell/CourseWorkspace` 的远程仓库文档。

目前已有的基础能力包括：

- CourseControl：课程校验、调度、构建、恢复、报告。
- Director：章节、镜头、引擎和旁白计划。
- Producer：生产订单、资源、用量、交付清单和增量指纹。
- MotionStudio、BlenderStudio、ManimSandbox：不同视觉生产引擎。
- RemotionStudio：时间线、字幕、旁白和最终合成。
- KnowledgeStudio：教材拆解、页码定位、Claim 与证据引用。
- `build/` 临时构建区与 `deliver/` 最终交付区。

这意味着我们是在现有生产系统上升级，不是重新开发一套系统。

**保留现有基础**

现有构建、渲染、恢复、哈希和交付机制继续使用。

**需要重点改造**

1. 人工分镜与 Director 生成物之间的单一数据源。
2. Animatic 的完整生产与审查流程。
3. Voice Bible、Lexicon 和旁白版本依赖。
4. Picture Lock、Dialogue Lock 的依赖失效机制。
5. 内容、视觉、工程、交付、发布五种状态的统一管理。
6. 真实长课程的端到端质量验证。

还有一个需要先处理的文档问题：内容根已于 2026-11-12 移到工作区外，但部分文档仍在用旧的内容目录描述。必须统一这些文档，否则后续开发会出现规范和实际代码不一致。

## 三、目标生产线：从课程构思到正式发布

### Course Production Pipeline V2.0

**01 · Knowledge Research**

教材、论文、新闻、产业资料 → 来源登记 → Claim → Evidence → 研究报告

**02 · Editorial Development**

选题 → 核心问题 → 课程大纲 → 讲稿 → 内容审查 → 人工批准

**03 · Visual Direction**

Shot Sheet → Director Plan → 资产设计 → 镜头制作

**04 · Animatic**

临时旁白 → 低分辨率画面 → 时间线预览 → 人工审查 → 反复修改

**05 · Picture Production**

正式场景 → 动画 → 三维 → 合成 → 画面审查 → Picture Lock

**06 · Sound Production**

Voice Bible → Lexicon → 正式旁白 → Dialogue Lock → 字幕 → 混音

**07 · Final Assembly & QC**

最终合成 → 内容复核 → 无声观看 → 声音复核 → 技术检查

**08 · Delivery & Release**

母版 → 字幕 → 项目资料 → 版权账本 → SHA-256 → 发布签核

这条生产线允许反复回退。例如，正式旁白修改后，可以让字幕、音频混音和受影响的时间线重新生成，而不必重新制作没有受到影响的三维场景。

## 四、正式实施任务分解

实施分为六个工作包，按照依赖关系执行。

### WP-0：生产规范与数据源梳理

先执行

目标：形成唯一的生产数据权威。

具体工作：

1. 对现有 `director-plan`、`storyboard.director.yaml`、`directions/`、`shot_specs/`、`plan.json` 做字段和依赖审计。
2. 确认现有 `storyboard.yaml`、`production.yaml`、Director Plan 的真实职责。
3. 定义 Shot Sheet 的人工编辑格式。
4. 定义 Shot Sheet 到现有生产契约的映射。
5. 保留历史课程的兼容读取能力。
6. 清理重复维护、相互覆盖的字段。

最终数据关系：

```text
Shot Sheet
    人工创作权威：镜头意图、内容、连续性、资产、证据、机位与转场
        │
        ▼
Director Compiler
    生成导演计划、方向文件、ShotSpec、现有 Storyboard 兼容数据
        │
        ▼
Existing Production Pipeline
    Engine Router → Renderer → Collect → Compose → Verify
```

Shot Sheet 的建议字段：

| 字段 | 内容 |
| --- | --- |
| shot_id | 唯一镜头 ID |
| scene_id | 场景 ID |
| purpose | 镜头表达目的 |
| narration_ref | 对应旁白段落 |
| visual_action | 画面实际发生的变化 |
| composition | 构图与机位 |
| continuity_refs | 跨镜头对象 ID |
| asset_refs | 资产引用 |
| evidence_refs | 数据、证据与来源 |
| transition | 前后镜头衔接方式 |
| director_notes | 导演备注 |

镜头时长由实际内容、声音和视觉设计共同确定，不在 Schema 中设定固定上下限。

### WP-1：Shot Sheet 与导演系统

目标：解决人工设计与机器执行之间的数据分叉。

交付：

- `shot-sheet.schema.json`
- `shot-sheet.yaml` 示例
- Shot Sheet Validator
- Director Compiler
- 旧 Director Plan 兼容适配器
- 连续性 ID 管理
- 镜头资产依赖追踪
- Shot Sheet 可视化审查报告

验收：

- 修改 Shot Sheet 后，所有下游文件能够重新生成。
- 未修改的镜头保持原有指纹。
- 同一对象跨镜头保持稳定身份引用。
- 缺失资产、错误证据引用、非法镜头关系能够准确定位。
- 旧课程能够继续构建，不要求一次性迁移所有历史课程。

### WP-2：Animatic 生产系统

最高优先级的生产能力

目标：让导演设计在正式渲染之前可以完整观看和调整。

实现一个正式命令：

```text
course-control animatic --lesson <slug>
```

输入：

- Shot Sheet
- 现有截图
- 临时旁白或参考音频
- 镜头方向和资产预览
- 当前时间线

输出：

```text
build/<slug>/animatic/
├── animatic.mp4
├── animatic.json
├── contact-sheet.png
├── timeline.json
├── audio/
├── frames/
└── animatic-report.json
```

Animatic 必须具备：

1. 按真实时间线播放。
2. 每个镜头能够显示镜号。
3. 临时旁白可以替换。
4. 允许静态画面、预览视频、简单三维预览混合。
5. 镜头之间可以硬切，也可以使用临时占位转场。
6. 可以单独替换一个镜头并重新生成。
7. 报告能够定位画面与声音的时间关系。

验收依据：完整观看 Animatic 后，能够判断叙事是否成立、画面是否有设计、视觉节奏是否合适，以及哪些地方需要返工。

480p 是默认预览输出，不是质量上限；分辨率与播放时间都不作为通过条件。

### WP-3：声音生产系统

目标：把音色、发音、旁白文本和时间线变成一套可追溯的生产资产。

交付结构：

```text
audio/
├── voice-bibles/
│   └── <voice-id>.yaml
├── lexicons/
│   └── <series-id>.yaml
└── narration/
    ├── scratch/
    └── final/
```

Voice Bible 负责：

- 参考声音文件及 SHA-256。
- 声线身份。
- 语言和发音风格。
- 语速、音高、音色倾向。
- 强调、停顿和情绪表达规范。
- TTS 后端及模型版本。
- 已批准的声音样例。

Lexicon 负责：

- 技术术语。
- 人名、公司名。
- 缩写。
- 数学符号与公式读法。
- 多音词及上下文读法。

TTS 缓存键必须包含文本、Voice Bible 版本、Lexicon 版本、模型版本和合成参数。

声音生产分为：

| 阶段 | 作用 |
| --- | --- |
| Scratch VO | 用于 Animatic，快速验证时序 |
| Final VO | 正式旁白，人工审听 |
| Dialogue Lock | 确认旁白文本与声音版本 |
| Subtitle Build | 基于正式旁白生成、校准字幕 |
| Audio Mix | VO、SFX、Music、Ambience 分轨混音 |

这里特别增加一条：Dialogue Lock 不锁死声音修改，而是锁定当前版本及其下游依赖。

### WP-4：画面锁定与版本管理

目标：解决画面、旁白、字幕之间的版本错配。

Picture Lock：

- 镜头版本清单。
- 画面文件 SHA-256。
- 场景与资产依赖。
- 画面审核记录。
- 锁定时使用的 Shot Sheet 版本。
- 当前画面版本的完整性报告。

Dialogue Lock：

- 正式旁白文本哈希。
- Voice Bible 版本。
- Lexicon 版本。
- 音频文件哈希。
- 实际音频时长。
- 旁白段落与字幕的对应关系。

依赖失效规则：

| 修改内容 | 需要重新验证的内容 |
| --- | --- |
| Shot Sheet | 导演计划、受影响镜头、Animatic |
| 单个镜头 | 对应画面、时间线、最终合成 |
| Voice Bible | 受影响旁白、字幕、混音 |
| Lexicon | 使用相关术语的旁白及其下游 |
| 旁白文本 | TTS、字幕、时间线、混音 |
| BGM / SFX | 混音与音频 QC |
| 最终合成配置 | 合成结果、全片 QC |

不受影响的资产和镜头继续复用。失效范围以依赖关系和哈希为准，不采用全量重做。

### WP-5：最终验收与交付

目标：把工程构建成功和真正的作品完成区分开。

最终质量报告采用五维状态（与代码现有状态的对应关系见 [基线审计 §5.6](P0-基线审计.md)）：

- ENGINEERING_VERIFIED
- CONTENT_VERIFIED
- VISUAL_VERIFIED
- PACKAGE_VERIFIED
- RELEASE_APPROVED

对应人工审查分成三种：

1. 静音观看：画面是否独立成立。
2. 纯声音审查：旁白是否自然、情绪是否合理、声音是否清楚。
3. 完整观看：知识、画面、声音、字幕和节奏是否共同成立。

交付包继续使用现有 `course-control package` 与 `package-verify`，不重新发明一套交付机制。

## 五、程序与课程的物理分离

这一点直接作为架构约束执行。

### A. CourseWorkspace（程序仓库）

GitHub：weixc0856-cell/CourseWorkspace

- CourseControl
- Renderer 与各类 Adapter
- Schema、Validator、CLI
- 自动化测试
- 生产规范与开发文档
- 可复用的视觉引擎与资产模板

### B. CourseContent（本地课程工作区）

独立于程序仓库，使用外部 content_root

- 课程大纲和教材资料
- Claim / Evidence
- 讲稿和分镜
- Voice Bible / Lexicon
- 镜头素材和场景文件
- Animatic 与正式成片
- 最终交付包

### C. BookIngest（独立资料工具）

- Docling
- PDF / EPUB 摄取
- Markdown、JSON、图片
- 转换质量报告
- 向课程知识库输出标准资料包

三个项目之间通过文件契约和版本化接口连接。

重要的工程决定：

- 程序仓库不提交真实课程、教材 PDF、旁白、视频、个人声音参考和交付包。
- 课程项目不复制 CourseControl 的源代码。
- CourseContent 记录所使用的程序版本或 Git Commit。
- 程序升级不能自动覆盖已有课程资产。
- 课程资料可以单独备份、迁移和归档。
- BookIngest 的转换逻辑不进入 CourseControl。

这样以后即使更换视频引擎、TTS 后端或者整个课程生产框架，课程知识资产仍然可以保留和迁移。

## 六、实际执行顺序

实施顺序不按开发时间排，而按依赖关系和交付风险排。

| 顺序 | 工作 | 具体交付 | 完成标志 |
| --- | --- | --- | --- |
| P0 | 基线审计 | 代码、Schema、数据流、目录审计 | 现状与文档一致 |
| P1 | Animatic | CLI、预览生成、时间线报告 | 真实长课可以反复预览 |
| P2 | 声音体系 | Voice Bible、Lexicon、缓存指纹 | 声音版本可追溯 |
| P3 | Shot Sheet | Schema、编辑源、Compiler | 分镜只有一个人工权威 |
| P4 | Lock 系统 | Picture / Dialogue Lock | 修改能准确触发下游更新 |
| P5 | 全链路验证 | 一门完整长课程 | 真实作品通过质量验收 |
| P6 | 正式生产 | 模板、文档、兼容性、交付 | 可以稳定用于后续课程 |

### 各阶段的具体验收标准

**P0：基线审计**

- 核实远程 `main` 实际提交。
- 核实本机 `content_root`。
- 检查已有命令是否重复。
- 检查旧课程兼容性。
- 更新 PRD、ARCHITECTURE、PROJECT_STATUS、ACCEPTANCE 的不一致部分。

**P1：Animatic**

- 至少使用一门真实长课程验证。
- 临时旁白与正式旁白可以切换。
- 镜头替换后可以局部更新。
- 时间线与音频同步。
- 输出可以独立播放的 Animatic。

**P2：声音**

- 两集引用同一个 Voice Bible 时，音色规范一致。
- 修改 Lexicon 能正确使相关语音缓存失效。
- 修改旁白后字幕和混音不会继续消费旧版本。
- 正式旁白可以独立试听和审核。

**P3：分镜**

- Shot Sheet 是唯一人工设计源。
- Director Plan、ShotSpec 等机器产物可以重新生成。
- 连续性关系可以跨镜头追踪。
- 旧课程不需要全部重写。

**P4：锁定机制**

- 能识别上游版本变化。
- 能定位受影响的下游资产。
- 不受影响的资产可以复用。
- 修改锁定内容后重新审查，而不是禁止修改。

**P5：真实课程验证**

选一门完整的 20 分钟课程，走完：

研究 → 脚本 → Shot Sheet → Animatic → 正式画面 → 正式旁白 → 字幕 → 混音 → QC → 人工审核 → 交付。

通过后才将这条路线定为正式 V2 生产流程。

## 八、这次改造的判断

有三件事必须特别重视：

第一，Animatic 是生产决策工具，不是一个新的视频播放器。

它最大的价值是让你在投入正式渲染资源之前，就能看到整集课程的视觉叙事是否成立。

第二，声音与画面必须独立生产，又必须能够精确同步。

旁白修改不能让所有动画失效，画面修改也不能导致重新生成全部语音。这是工业化生产真正能降低成本的地方。

第三，程序的自动化程度不代表课程质量。

即使所有命令都通过，如果成片仍然像一份不断切换的 PPT，生产任务依然没有完成。
